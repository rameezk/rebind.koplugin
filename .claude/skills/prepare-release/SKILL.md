# Prepare release

Rebind releases through release-please. Every push to `main` makes the `release`
workflow regenerate the open `chore(main): release X.Y.Z` pull request, and when
that pull request is merged release-please publishes a GitHub release whose notes
are taken from the pull request body.

The generated body is only a list of commit subjects. This skill puts a short,
friendly write-up for people who use Rebind on their e-reader above that list,
keeps the plain list underneath, and then makes sure the write-up is still there
on the published release.

Look at the `v2.3.0` and `v2.4.0` releases (`gh release view v2.4.0`) before
writing. They are the reference for tone, length and layout.

## Where the notes live and what overwrites them

- **The release pull request body** is what release-please reads when it
  publishes the release. release-please rewrites the whole body every time
  `main` moves while the pull request is open, which silently drops the
  write-up. This is the override to guard against.
- **The GitHub release** is created from the body as it is at merge time. It
  can be edited afterwards with `gh release edit`, and release-please never
  touches it again.
- **`CHANGELOG.md`** is generated by release-please and only ever holds the
  plain list. Never edit it, in the release branch or anywhere else.

## Steps

### 1. Find the release pull request

```sh
gh pr list --state open --json number,title,headRefName,body \
  --jq '[.[] | select(.title | startswith("chore(main): release "))]'
```

Filter on the title with `--jq` rather than `--search`. GitHub's search drops
the parentheses in `chore(main)`, so a title search finds nothing even when
the release pull request is open.

If there is none, say so and stop. If `main` has commits since the pull request
was last updated, wait for the `release` workflow run on `main` to finish
(`gh run list --workflow release.yml --branch main --limit 3`) so the
generated body is current before writing anything.

### 2. Gather what changed

- The `feat` and `fix` entries in the generated body are the scope. Hidden
  types (`chore`, `docs`, `test`, `ci`, `refactor`, `perf`) do not appear in
  the write-up.
- Read each linked pull request (`gh pr view <n> --json title,body`) for what
  the change does on the device.
- Check UI labels, menu paths and limits against the code under `rebind/`
  rather than trusting pull request text, since later pull requests may have
  renamed or changed them.
- Read `docs/CONTEXT.md` so domain words are used the way the project uses
  them.

### 3. Write the friendly notes

Shape, following `v2.3.0` and `v2.4.0`:

1. One sentence that says what this release lets you do, starting with
   "Rebind can now ..." or similar.
2. A short paragraph on the problem it solves and how it feels to use, from
   the point of view of someone fixing books on their device.
3. `###` sections grouping the changes by what the reader is doing (for
   example "Adding a cover", "Starting a batch", "Safeguards"), each with short
   bullets or a short paragraph. A small release can skip the sections and use
   a single list of bullets.
4. An "Also new" or "Also fixed" section for small, unrelated changes and for
   bug fixes a person would have noticed.

Writing rules:

- Plain language for a reader, not a developer. No commit hashes, pull request
  numbers, file names, function names or provider API details.
- Use the exact UI labels in quotes, and menu paths with arrows, as in
  `Tools → Rebind → Rebind several books…`.
- Glossary terms from `docs/CONTEXT.md` are plain lowercase words in natural
  sentences, never capitalised proper nouns.
- Never use the em dash. Use a plain dash, or better, a new sentence.
- Never put a line that is only `---` in the notes. release-please uses those
  lines to find the notes in the body.
- Do not repeat the generated list in prose; describe the experience and let
  the list below cover the individual changes.

### 4. Show the draft and get approval

Show the user the full write-up and wait for their go-ahead before touching the
pull request. Apply their edits and show it again until they approve.

### 5. Apply it to the pull request body

Work in a scratch directory outside the repo, called `$SCRATCH` below. Save
the current body, insert the write-up, and write it back:

```sh
gh pr view <n> --json body -q .body > "$SCRATCH/release-body.md"
```

Edit `release-body.md` so that it reads, in order:

1. Everything up to and including the `## [X.Y.Z](...) (date)` heading line,
   unchanged.
2. A blank line, then the approved write-up.
3. A blank line, then the generated `### Features` and `### Bug Fixes`
   sections, unchanged.
4. The closing `---` line and the release-please footer, unchanged.

Keep the release-please header (`:robot: I have created a release ...` and the
`---` under it) and footer exactly as they were. Then:

```sh
gh pr edit <n> --body-file "$SCRATCH/release-body.md"
gh pr view <n> --json body -q .body
```

Confirm the write-up and the plain list are both in the body, and keep
`release-body.md` around for the following steps.

### 6. Keep it there until merge

Tell the user that any merge to `main` before the release pull request is
merged will make release-please rewrite the body and drop the write-up.

Before the release pull request is merged, whether the user merges it or asks
you to:

1. Check that no `release` workflow run on `main` is still in progress.
2. Read the body again and check the write-up is still there.
3. If it is gone, release-please has regenerated it. Take the new body, which
   may list more changes, update the write-up to cover any new `feat` or `fix`
   entries, show the changes to the user, and apply it again as in step 5.

Only merge if the user asks you to. Never merge it on your own.

### 7. Check the published release

After the release pull request is merged, wait for the `release` workflow run
on `main` to finish and for the release to exist:

```sh
gh run list --workflow release.yml --branch main --limit 1
gh release view vX.Y.Z --json body,assets -q '.body, (.assets[].name)'
```

- If the release body has the write-up followed by the plain list, it stuck.
- If the write-up is missing, build the release notes from the approved
  write-up and the plain list the release did get, in the same layout as
  `v2.4.0` (the `## [X.Y.Z](...)` heading, the write-up, then the generated
  sections), and apply it:

  ```sh
  gh release edit vX.Y.Z --notes-file "$SCRATCH/release-notes.md"
  gh release view vX.Y.Z --json body -q .body
  ```

- Check that `rebind.koplugin.zip` is attached. If the build step failed,
  report the failed run instead of attaching anything by hand.

Report the release URL and whether the write-up made it through on the first
try or had to be put back.
